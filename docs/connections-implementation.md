# Reusable Connections

Administrator authentication protects every product API. Native HTTPS, operator-only owner provisioning and deployment configuration are described in [administrator authentication](admin-auth-completion.md). Automated execution still uses fake adapters.

## Implemented boundaries

- Existing Connection remains the reusable account/authority identity. Stable
  IDs/keys are reused across immutable automation versions and run evidence.
- `credential_secrets` contains only AES-256-GCM authenticated envelopes and safe
  format/provider metadata. A nullable Connection FK replaces free-form references
  for new credentials; legacy `credential_ref` placeholders remain migration-safe
  but cannot prove usable live access.
- Server-only `CredentialCrypto` uses a fresh 12-byte nonce, 16-byte tag and
  record/provider/auth-type-bound AAD. Reads have no plaintext fallback.
- Deployment keyring is supplied through `ATLAS_CREDENTIAL_KEYS_FILE` or
  `ATLAS_CREDENTIAL_KEYS`; `ATLAS_CREDENTIAL_ACTIVE_KEY` chooses new-write version.
  Keys are never generated by the server and must remain separate from Postgres,
  source control, image layers, logs and normal database backups.
- API-key forms and Google installation-client configuration are write-only.
  Metadata DTOs never expose keys, encrypted envelopes or OAuth tokens.
- Fixed official-provider probes cover OpenAI model-list access, Anthropic
  model-list access and Telegram bot identity. These are not generation tests
  and do not prove permission to invoke a chosen model. Model-provider account
  identity cannot be inferred from a models list; it remains explicitly unknown.
- Google uses authorization-code + S256 PKCE, a session-bound expiring one-use
  state record, offline refresh, trusted-provider identity lookup, actual returned
  grants, same-account reconnect and sanitized terminal/transient errors.
- Refresh/replace/disable/forget share a database row lock. Successful refresh is
  persisted even if a subsequent account probe fails. Token refresh does not
  create spurious configuration-revision conflicts. Returned reduced grants are
  saved and block live resolution. Remote refresh and local commit cannot be an
  atomic distributed transaction; an uncertain rotating-token commit can require
  reconnect.
- Callback final writes validate the current installation-client revision inside
  the committing transaction. Pending authorizations are serialized per session.
- Local disable keeps encrypted credentials; explicit Resume restores eligible
  locally disabled connections. Forget removes the active secret. Archive retains
  historical Connection references. Provider-side Google revocation is separate,
  can affect the account's broader project grant and may fail independently.
- Email Triage's mailbox and model selector creates a new immutable version.
  Semantics/operations stay fixed, all Gmail bindings must select the same mailbox,
  and model credentials remain separate from model name/prompt. ModelInvocation
  records the selected Connection FK and exposes its ID in read evidence.
- Test-run composition still always uses fake adapters. Fake recovery still
  uses persisted fake mailbox state and historical action/run/version identity.
  Neither saving bindings nor running existing fake tests enables live Gmail,
  Telegram or model effects. Live preflight now requires an actual credential
  resolver in addition to presence/provider checks; no resolver fails closed.

## Administrator authentication and composition

Migration 0006 creates the four authentication tables. Public signup, social login and unreviewed auth routes are closed. The fixed owner uses a 12-hour nonrenewing database session and must sign in within the last 15 minutes before changing credentials or automation bindings. API mutations require exact-origin JSON over native HTTPS. Session DTOs and auth success responses contain no bearer token.

`apps/api/src/app.ts` initializes and authenticates credential storage before constructing either Settings router. The allowlisted auth handler is registered first; owner middleware precedes every existing product route. The same Hono Context supplies the verified database session ID to Google's state/PKCE flow. Native TLS and same-origin compiled web assets are supported through `transport.ts`; forwarded headers are not a trusted transport substitute.

All auth mutations lock the owner row in an outer database transaction. This serializes login with password changes and makes password updates, session deletion and replacement-session creation commit or roll back together. Better Auth's unexpected errors propagate to the sanitizing boundary; this prevents Better Call's fallback console output from exposing SQL parameters even when library logging is disabled.

The operator-only provisioning command accepts bounded JSON through stdin and requires `--apply`, explicit database configuration and valid auth deployment configuration. It never runs at startup and cannot overwrite an existing owner.

### Registered-router contract

- `connectionRoutes(service, security)` receives `requireOwner`,
  `requireFreshOwner`, and `sessionId(context): string`. Both middleware must
  derive identity from a verified server-side session, never a request header or
  body. `sessionId` returns that same authenticated initiating session ID.
- `automationConnectionRoutes(bindingService, security)` receives the same owner
  and fresh-owner middleware. Factories must never receive no-op substitutes.
- Owner middleware enforces valid deployment configuration, trusted HTTPS request
  transport, unexpired/unrevoked session, and the fixed provisioned owner's ID.
  Missing configuration returns 503; absent/invalid session 401; other user 403.
- Fresh-owner middleware repeats owner checks, requires session authentication
  within 15 minutes, exact canonical Origin and application/json for unsafe
  methods. Reject missing/foreign Origin, cross-site unsafe requests, and non-JSON
  writes. Do not infer trusted transport from arbitrary forwarded headers.
- Credential GET metadata and Google callback require owner; every non-GET
  credential endpoint additionally requires fresh owner. Binding POST explicitly
  requires fresh owner. Callback is a cross-site top-level GET and must remain
  eligible under same-session, one-use state/PKCE validation; no blanket
  cross-site-GET rejection.
- Mount both factories at root because they already declare full
  `/api/settings/...` paths. Apply owner checks to all existing API reads, writes
  and run routes too; mounting an auth handler alone does not protect them.
- Configure no wildcard CORS, no-store responses, secure host-only session cookie,
  allowlisted auth endpoints, and sanitized errors without raw request/provider
  logging. Redact auth session tokens from JSON while retaining Set-Cookie.
- Await storage initialization first, then create the Connection service using
  its validated crypto and fixed canonical HTTPS origin. Register routers only
  after real auth is complete. Full authenticated E2E must prove these contracts.

## Key recovery and rotation

Keep database backups and required key versions in separate protected locations.
Restoring ciphertext without its key does not recover credentials. Missing/wrong
keys must leave credential-dependent operations blocked; re-enter keys/reconnect
accounts after irrecoverable key loss while preserving history. Database deletion
cannot erase old backups, which remain subject to retention policy.

A keyring can decrypt old versions while new writes use a new active version.
The implementation includes `connections/key-maintenance.ts` and the local
`credential-keys.ts` operator command. Await `initializeCredentialStorage(db, env)`
before mounting credential routes, constructing live resolvers, or listening.
It authenticates every credential and pending OAuth-verifier envelope in a
repeatable-read snapshot. Missing keys, wrong keys, malformed data, or inaccessible
schema fail closed with a sanitized error. Empty storage can remain unconfigured;
credential writes remain unavailable until a deployment keyring is supplied.
The entrypoint awaits this initializer before any router is constructed or listener starts.

Operator procedure, after specific deployment authorization:

1. Drain all API/worker writers. Verify a database backup and a separate protected
   backup of every key version required by that database. Preserve both through
   the normal retention window; the command never deletes keys or backups.
2. Configure the new active key version together with every previous version.
   No key is generated or provisioned by this code.
3. From the repository root run
   `pnpm --filter api exec tsx src/credential-keys.ts validate`.
4. Run `pnpm --filter api exec tsx src/credential-keys.ts rotate --apply --writers-stopped --backup-verified`.
   These flags attest operator prerequisites; they do not verify deployment state.
   Each transaction handles at most 100 records; each invocation handles at most
   10 batches. If output says `resume_required`, repeat the same command.
5. Validate again; resume all writers with the same active key configuration.
   Only after full validation and writer-version coordination may old keys leave
   the active runtime keyring. Old backups still require those old keys separately.

Rotation uses a maintenance advisory lock and short writer-table locks, with
5-second lock timeout and 30-second statement timeout. Each committed batch is
its checkpoint; interruption resumes by stored key version. Failure rolls back
that batch. Secret-record revisions advance; Connection and OAuth-client revisions
stay stable because identity and plaintext are unchanged. Concurrent replacement
cannot be overwritten, but old writers can create old-version records later,
which is why draining writers is mandatory for completion and key retirement.
The startup scan intentionally includes expired pending attempts; explicit
maintenance/normal attempt cleanup can remove these later, not silently discard
unreadable ciphertext.

The new maintenance test helper covers wrong/missing keys, rollback/resume,
prototype-named key versions, lock contention, stable revisions, concurrent
replacement, old-backup key requirements and CLI redaction. These checks are part of the combined isolated verification gate, using owned disposable databases and synthetic in-memory keys. Authenticated API and native-HTTPS browser verification also use real owner middleware and synthetic credentials.
A compromise also requires provider-token/key response; re-encryption does not
undo disclosure.
The isolated verification restores a synthetic database and decrypts restored
credentials using the original in-memory key, without provisioning deployment keys.

## Verification

Run from the repository root with the pinned pnpm version:

- `pnpm typecheck --concurrency=1`
- `pnpm lint --concurrency=1`
- `pnpm check:boundaries`
- `pnpm --filter api test`
- `node scripts/verify-connections.mjs` (owns random isolated databases and fake mailbox directory)
- `node scripts/verify-key-maintenance.mjs` (independent synthetic key-rotation database)
- `node scripts/verify-message-admission.mjs`
- `node scripts/verify-archive-recovery.mjs`
- `pnpm --filter web exec playwright test --config connections.playwright.config.ts` (all API mocked)

The test matrix covers AEAD tampering/context swaps/wrong keys, key-version
compatibility, sanitized provider failures, fixed read-only probes, PKCE, OAuth
state replay/session mismatch, identity mismatch, rotated-refresh preservation,
refresh concurrency, client-change races, replacement rollback, archive FK
history preservation, immutable binding versions and old-run evidence.

Authentication and native-HTTPS browser checks are included in `pnpm verify`. The earlier mocked UI suite remains useful for error, cancellation and binding states and is explicitly separate from real-auth evidence.

## Remaining deployment steps

- Choose the real canonical HTTPS origin and supply its certificate/private key through protected configuration. The implemented path terminates TLS natively; an ingress trust contract has not been enabled.
- Verify a database backup and restoration with separately protected versions of every credential key before applying unapplied migrations.
- Supply administrator auth and credential-encryption secrets outside Git/database backups. Provision the actual owner with the explicit local operator command; no default or automatic owner is provided.
- Approve restart and point the web-assets path at the reviewed candidate build. Actual provider credentials, Google OAuth client setup/consent and external calls remain operator actions.
- Live Gmail/model/Telegram execution adapters remain outside this Connections/authentication task. Existing automated test runs and recovery continue using fake adapters.

## Build/preview isolation

The canonical preview serves `apps/web/dist` directly. **Never run a candidate
build into that directory.** Use an explicit separate output, for example:

`pnpm --filter web exec vite build --outDir ../../audit/connections/web-build-candidate`

`pnpm --filter api exec tsc -p tsconfig.build.json --outDir ../../audit/connections/api-build-candidate`
